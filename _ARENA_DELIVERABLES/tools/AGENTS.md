# قرارداد ایجنت — فروشگاه پوشاک کودک و نوجوان

> این فایل باید در **ریشه پروژه** قرار بگیرد. هر ایجنت هوش مصنوعی قبل از هر کاری آن را می‌خواند.
> هدف: ایجنت بتواند مستقل کار کند، بدون اینکه چیزی را خراب کند.

---

## ۱) این پروژه چیست

فروشگاه اینترنتی پوشاک کودک و نوجوان با Next.js + MySQL، میزبانی روی cPanel،
با اتوماسیون کامل انتشار در شبکه‌های اجتماعی و پرو آنلاین لباس.

**مخاطب:** بازار ایران. زبان رابط کاربری و محتوا: **فارسی، راست‌چین (RTL)**.

---

## ۲) قوانین محیط (بسیار مهم)

### ⛔ هرگز روی سرور میزبان‌فا این کارها را نکن
```
git clone / git pull        ← تحریم، ساعت‌ها طول می‌کشد
npm install / npm ci        ← timeout می‌خورد
docker pull                 ← اصلاً کار نمی‌کند
هر دانلودی از گیت‌هاب       ← کند یا مسدود
```

### ✅ به‌جایش
همه کارهای سنگین روی **GitHub Actions** انجام می‌شود.
سرور فقط یک فایل `tar.gz` می‌گیرد و باز می‌کند.

### تقسیم سرورها
| سرور | مسئولیت | محدودیت |
|---|---|---|
| **میزبان‌فا (ایران)** | سایت، دیتابیس، درگاه پرداخت، پیامک | دسترسی به سرویس‌های خارجی ندارد |
| **هاستینگر (خارج)** | موتور AI، انتشار اینستاگرام/پینترست/یوتیوب | نباید دیتای حساس مشتری نگه دارد |

**قانون:** هر کدی که به `graph.facebook.com` یا `agentrouter.org` وصل می‌شود،
باید در پوشه `engine/` باشد که روی هاستینگر دیپلوی می‌شود — نه در `app/`.

## ۴) دستورات استاندارد

هر کاری باید با یک دستور انجام شود. اگر کاری دستی است، یعنی هنوز اسکریپتش نوشته نشده.

```bash
npm run doctor      # تشخیص سلامت محیط توسعه
npm run dev         # اجرای محلی
npm run build       # ساخت production
npm run verify      # ★ تست کامل — بعد از هر تغییر اجباری
npm run test        # تست‌های واحد
npm run lint        # بررسی کد
npm run db:migrate  # اجرای migration ها
npm run db:seed     # داده نمونه
npm run deploy:stg  # دیپلوی روی staging
npm run deploy:prod # دیپلوی production (فقط با تأیید انسان)
npm run rollback    # بازگشت به نسخه قبل
```

## ۵) چرخه کار اجباری ایجنت

```
۱) بخوان: AGENTS.md + فایل‌های مرتبط
۲) برنامه بده: چه فایل‌هایی، چه تغییری، چه ریسکی
۳) کد بنویس در یک برنچ جدا (هرگز مستقیم روی main)
۴) npm run verify  ← اگر قرمز شد، درست کن؛ کار ناتمام تحویل نده
۵) دیپلوی staging + health check
۶) گزارش بده: چه شد، چه چیزی تست شد، چه چیزی نشد
۷) منتظر تأیید انسان برای production
```

### ⚠️ قانون طلایی
> اگر نتوانستی نتیجه کارت را **خودت تأیید کنی**، آن را تحویل نده.
> «فکر می‌کنم کار می‌کند» قابل قبول نیست. «تست کردم، این خروجی است» قابل قبول است.

## ۶) خود-تأییدی (Self-Verification)

`npm run verify` باید این‌ها را چک کند:

| بررسی | ابزار |
|---|---|
| کد کامپایل می‌شود | `tsc --noEmit` |
| lint پاس می‌شود | `eslint` |
| تست‌ها سبز است | `vitest` |
| build موفق است | `next build` |
| صفحات کلیدی رندر می‌شوند | smoke test |
| دیتابیس متصل است | `/api/health?db=1` |
| کلیدی در کد hardcode نشده | `gitleaks` یا regex |
| اندازه bundle از حد نگذشته | bundle analyzer |

### Endpointهای سلامت
```
GET /api/health              → زنده بودن + نسخه + کامیت
GET /api/health?db=1         → اتصال دیتابیس
GET /api/health?deep=1       → همه سرویس‌ها
GET /api/admin/integrations-test  → توکن‌های شبکه‌های اجتماعی
GET /api/admin/ai-test       → AgentRouter + تأخیر
```

## ۷) گاردریل‌های ایمنی

| گاردریل | نحوه کار |
|---|---|
| **کلید قرمز** | `AUTOMATION_MODE=PAUSE` → همه اتوماسیون فوراً متوقف |
| **حالت خشک** | `DRY_RUN=true` → هیچ پیام واقعی ارسال نمی‌شود، فقط لاگ |
| **سقف هزینه AI** | `AI_DAILY_BUDGET_USD` → بعد از رسیدن، توقف |
| **سقف پیامک** | `SMS_DAILY_LIMIT` → جلوگیری از هزینه ناگهانی |
| **بازگشت خودکار** | health check قرمز بعد از دیپلوی → rollback |
| **جداسازی محیط** | staging دیتابیس کاملاً جدا دارد |
| **لاگ حسابرسی** | هر تغییر قیمت/موجودی/انتشار در `audit_log` |

## ۸) استانداردهای کد

```
زبان کد          TypeScript (strict)
استایل           Tailwind، RTL-first
نام‌گذاری فایل    kebab-case
نام‌گذاری کامپوننت PascalCase
توابع            camelCase
ثابت‌ها           SCREAMING_SNAKE
کامنت‌ها          فارسی برای منطق کسب‌وکار، انگلیسی برای فنی
پیام کامیت       فارسی یا انگلیسی روشن، با prefix: feat/fix/docs/refactor
```

### الزامات RTL
- همه صفحات `dir="rtl"`
- استفاده از `ms-*`/`me-*` به‌جای `ml-*`/`mr-*`
- اعداد فارسی در نمایش، انگلیسی در دیتابیس
- تاریخ شمسی در رابط کاربری، میلادی در دیتابیس

## ۹) ساختار پروژه

```
app/            صفحات و API — روی میزبان‌فا
  (shop)/       فروشگاه عمومی
  (seller)/     پنل فروشنده
  (admin)/      پنل مدیریت
  api/          endpointها
engine/         ★ کدی که به سرویس‌های خارجی وصل می‌شود — روی هاستینگر
lib/            منطق مشترک
  ai/           AgentRouter
  queue/        صف (mysql | redis)
  storage/      فایل (fs | s3)
  search/       جستجو (mysql | meili)
  social/       انتشار شبکه‌های اجتماعی
  tryon/        پرو آنلاین
db/migrations/  مهاجرت‌های شماره‌گذاری‌شده
tools/          اسکریپت‌های دیپلوی و تشخیص
tests/          تست‌ها
docs/           مستندات
```

### لایه انتزاع اجباری
`lib/queue/`, `lib/storage/`, `lib/search/` باید **interface یکسان** داشته باشند
با پیاده‌سازی‌های متفاوت. انتخاب با متغیر محیطی:
```bash
QUEUE_DRIVER=mysql    # mysql | redis
STORAGE_DRIVER=fs     # fs | s3
SEARCH_DRIVER=mysql   # mysql | meili
```
این باعث می‌شود مهاجرت cPanel → VPS بدون تغییر کد انجام شود.

## ۱۱) وقتی گیر کردی

1. **مبهم بود؟** بپرس، حدس نزن.
2. **verify قرمز شد؟** درست کن، دور نزن.
3. **نیاز به کلید داشتی؟** از انسان بخواه، هرگز کلید نساز یا حدس نزن.
4. **تغییر بزرگ لازم است؟** اول برنامه بده، بعد اجرا کن.
5. **مطمئن نیستی مجاز است؟** فرض کن ممنوع است و بپرس.

# مانع ۱ — نداشتن SSH روی میزبان‌فا

## ۱٫۱ چرا SSH نمی‌دهند و چرا اصرار نکنیم

هاست اشتراکی معمولاً SSH را غیرفعال می‌کند چون یک کاربر می‌تواند منابع بقیه را مصرف کند. حتی اگر بدهند، معمولاً **jailed shell** با ابزار محدود است. پس به‌جای جنگیدن با هاست، مسیری می‌سازیم که اصلاً SSH لازم نداشته باشد.

## ۱٫۲ اول این سه گزینه را از پشتیبانی بخواهید (رایگان، شاید جواب بدهد)

به ترتیب اولویت از پشتیبانی میزبان‌فا بپرسید:

| درخواست | متن پیشنهادی تیکت |
|---|---|
| **الف) Terminal داخل cPanel** | «لطفاً ویژگی Terminal را در cPanel اکانت من فعال کنید. نیازی به دسترسی SSH از بیرون ندارم، فقط ترمینال داخل پنل کافی است.» |
| **ب) SSH با کلید** | «لطفاً SSH Access را با احراز هویت کلید عمومی (نه پسورد) برای اکانت من فعال کنید. کلید public را ضمیمه کرده‌ام. پورت و آدرس را اعلام بفرمایید.» |
| **ج) API Token** | «لطفاً امکان ساخت cPanel API Token را در بخش Manage API Tokens فعال کنید.» |

**نکته مهم:** گزینه (ج) از هر دوی قبلی مهم‌تر است. اگر فقط یکی را بدهند، همین را بخواهید.

## ۱٫۳ راه‌حل اصلی: cPanel API Token — جایگزین کامل SSH

cPanel یک API کامل روی HTTPS (پورت ۲۰۸۳) دارد که تقریباً هر کاری که با SSH می‌کردیم را انجام می‌دهد — **بدون نیاز به SSH**.

### ساخت توکن
```
cPanel → Security → Manage API Tokens → Create
نام: github-deploy
دسترسی: Full (یا محدود به Fileman + Archive اگر ممکن بود)
→ توکن ۳۲ کاراکتری را کپی کنید (فقط یک بار نشان داده می‌شود)
```

### کارهایی که با API می‌شود کرد

| کار | Endpoint | معادل SSH |
|---|---|---|
| آپلود فایل | `UAPI Fileman::upload_files` | `scp` |
| استخراج tar.gz | `UAPI Archive::extract_archive` | `tar -xzf` |
| ساخت پوشه | `UAPI Fileman::mkdir` | `mkdir` |
| حذف فایل | `UAPI Fileman::trash_files` | `rm` |
| ری‌استارت اپ Node | نوشتن در `tmp/restart.txt` | `touch tmp/restart.txt` |
| مدیریت Cron | `UAPI Cron::add_line` | `crontab -e` |
| بکاپ دیتابیس | `UAPI Backup::…` | `mysqldump` |
| خواندن لاگ | `UAPI Fileman::get_file_content` | `cat` |

### نمونه فراخوانی (تست دستی)
```bash
# تست اتصال — باید لیست فایل‌ها را برگرداند
curl -sS -H 'Authorization: cpanel USERNAME:APITOKEN' \
  'https://HOST:2083/execute/Fileman/list_files?dir=%2Fhome%2FUSERNAME'

# آپلود بسته
curl -sS -H 'Authorization: cpanel USERNAME:APITOKEN' \
  -F 'dir=/home/USERNAME/incoming' \
  -F 'file-1=@bundle.tar.gz' \
  'https://HOST:2083/execute/Fileman/upload_files'

# استخراج روی سرور
curl -sS -H 'Authorization: cpanel USERNAME:APITOKEN' \
  --data-urlencode 'sourcefiles=/home/USERNAME/incoming/bundle.tar.gz' \
  --data-urlencode 'destdir=/home/USERNAME/app' \
  'https://HOST:2083/execute/Archive/extract_archive'
```

## ۱٫۴ راه‌حل پشتیبان: PHP Deploy Receiver

اگر حتی API Token هم ندادند، یک فایل PHP کوچک روی هاست می‌گذاریم که نقش «گیرنده دیپلوی» را بازی می‌کند. فقط FTP لازم است (که همه هاست‌ها می‌دهند).

فایل `_deploy/receive.php` در بسته تحویلی هست. کارش:
1. درخواست را با امضای HMAC اعتبارسنجی می‌کند (بدون امضای درست، ۴۰۳)
2. فایل tar.gz را می‌گیرد
3. بکاپ نسخه فعلی را می‌سازد
4. استخراج می‌کند و `.env` را دست‌نخورده نگه می‌دارد
5. `tmp/restart.txt` را لمس می‌کند تا اپ Node ری‌استارت شود
6. Health check می‌زند و نتیجه را JSON برمی‌گرداند
7. اگر خطا بود، **خودکار به نسخه قبل برمی‌گردد**

**امنیت:** بدون `DEPLOY_SECRET` هیچ‌کاری نمی‌کند، محدود به IP‌های GitHub Actions قابل تنظیم است، و بعد از هر دیپلوی لاگ می‌نویسد.

## ۱٫۵ اولویت پیاده‌سازی

```
۱) تیکت بزنید برای API Token          ← بهترین حالت
۲) اگر ندادند: PHP Receiver           ← همیشه کار می‌کند
۳) اگر SSH دادند: عالی، هر سه را داریم
```

**نتیجه: مانع ۱ به‌طور کامل قابل حل است و SSH اصلاً ضروری نیست.**

# مانع ۲ — کندی شدید گیت‌هاب روی میزبان‌فا

## ۲٫۱ ریشه واقعی مشکل

گیت‌هاب، npm registry و بسیاری از سرویس‌های توسعه، ترافیک از IP ایران را throttle یا مسدود می‌کنند. وقتی روی هاست `git pull` یا `npm install` می‌زنید، ممکن است ساعت‌ها طول بکشد یا timeout بخورد.

## ۲٫۲ راه‌حل بنیادی: معکوس کردن جهت جریان

**قانون طلایی این پروژه:**

> ❌ هرگز روی هاست میزبان‌فا دستور `git`، `npm install` یا `docker pull` اجرا نکنید.
> ✅ هاست فقط یک فایل آماده دریافت می‌کند و آن را باز می‌کند.

```
  ❌ روش غلط (کند و شکننده)
  ┌──────────┐  git pull   ┌──────────┐
  │ میزبان‌فا │ ─────────►  │ گیت‌هاب  │   ← ترافیک از ایران به بیرون
  │          │  npm install│  npm     │      = تحریم، کندی، timeout
  └──────────┘             └──────────┘

  ✅ روش درست (سریع و پایدار)
  ┌──────────┐   build     ┌──────────┐  push یک فایل  ┌──────────┐
  │ گیت‌هاب  │ ─────────►  │ Actions  │ ────────────►  │ میزبان‌فا │
  │          │  npm ci     │ (ابری)   │  ~۱۵ مگابایت   │          │
  └──────────┘             └──────────┘                └──────────┘
                            ↑ اینجا اینترنت آزاد است      ↑ فقط دریافت
```

همه کارهای سنگین (نصب پکیج، build، بهینه‌سازی) روی سرورهای GitHub Actions انجام می‌شود که اینترنت آزاد دارند. هاست ایرانی فقط **یک فایل فشرده** می‌گیرد.

## ۲٫۳ مشکل دوم: FTP فایل‌به‌فایل هم کند است

روش فعلی شما (`FTP-Deploy-Action`) هزاران فایل را یکی‌یکی sync می‌کند. روی هاست اشتراکی این فاجعه است.

### مقایسه روش‌ها

| روش | تعداد اتصال | زمان تخمینی | پایداری |
|---|---|---|---|
| ❌ FTP فایل‌به‌فایل (فعلی) | ۳٬۰۰۰+ | ۱۵-۴۰ دقیقه | ضعیف — نصفه می‌ماند |
| ⚠️ rsync روی SSH | ۱ | ۲-۴ دقیقه | خوب (ولی SSH لازم) |
| ✅ **یک tar.gz + استخراج با API** | **۲** | **۴۰-۹۰ ثانیه** | **عالی** |

### چرا این‌قدر تفاوت دارد
یک اتصال FTP روی شبکه پرتأخیر، برای هر فایل باید handshake کند. با ۳٬۰۰۰ فایل یعنی ۳٬۰۰۰ رفت‌وبرگشت. با tar.gz فقط یک آپلود داریم و استخراج **روی خود سرور** انجام می‌شود که سریع است.

## ۲٫۴ بهینه‌سازی‌های تکمیلی

| تکنیک | تأثیر |
|---|---|
| **حذف `node_modules` از بسته** | حجم از ۸۰ مگ به ۱۵ مگ — Next.js standalone فقط پکیج‌های لازم را کنار می‌گذارد |
| **دیپلوی افزایشی (Delta)** | فقط فایل‌های تغییرکرده در بسته باشند — حجم به ۲-۵ مگ |
| **فشرده‌سازی حداکثری** | `tar -czf` با `-9` یا استفاده از `zstd` |
| **کش GitHub Actions** | build از ۶ دقیقه به ۹۰ ثانیه |
| **دیپلوی از هاستینگر به‌عنوان رله** | اگر GitHub→میزبان‌فا کند بود: GitHub→هاستینگر→میزبان‌فا |

## ۲٫۵ اگر مجبور شدید روی هاست npm بزنید

فقط در حالت اضطراری — با آینه ایرانی:

```bash
npm config set registry https://mirror-npm.runflare.com
# یا
npm config set registry https://registry.npmmirror.com
npm config set strict-ssl false     # فقط اگر خطای گواهی داد
```

و DNS شکن یا ۴۰۳ روی سرور. ولی **این حالت نباید در معماری ما پیش بیاید.**

## ۲٫۶ ابزار تحویلی

در بسته این فایل‌ها هست:
- `.github/workflows/deploy-fast.yml` — بیلد و دیپلوی سریع بدون SSH
- `scripts/deploy-via-cpanel-api.sh` — آپلود و استخراج با API
- `_deploy/receive.php` — گیرنده PHP (پشتیبان)

**نتیجه: زمان دیپلوی از ۱۵-۴۰ دقیقه به زیر ۹۰ ثانیه می‌رسد.**

# مانع ۳ — عدم دسترسی به API اینستاگرام

این پیچیده‌ترین مانع است و باید صادقانه با آن روبه‌رو شویم. **دو مشکل کاملاً جدا** وجود دارد که اغلب با هم اشتباه گرفته می‌شوند.

## ۳٫۱ مشکل الف: IP ایران

سرورهای متا درخواست از IP ایران را رد می‌کنند.

**راه‌حل: قطعی و ساده.** موتور انتشار روی **هاستینگر (خارج از ایران)** اجرا می‌شود، نه روی میزبان‌فا. این دقیقاً همان معماری دومرحله‌ای است که در سند ۲ طراحی کردیم. پس این نیمه‌ی مشکل، **از قبل حل شده است**.

```
میزبان‌فا (ایران)              هاستینگر (خارج)           متا
  سایت، سفارش    ──HTTPS──►    موتور انتشار    ──API──►   اینستاگرام
  دیتابیس                       AgentRouter                فیسبوک
```

## ۳٫۲ مشکل ب: App Review متا (مانع اصلی)

این بخش سخت است. برای انتشار خودکار روی اینستاگرام، متا این‌ها را الزامی کرده:

| پیش‌نیاز | توضیح |
|---|---|
| اکانت **Professional** (Business یا Creator) | اکانت شخصی اصلاً کار نمی‌کند |
| **صفحه فیسبوک** متصل | حتی اگر هرگز در فیسبوک پست نکنید |
| اپ در Meta for Developers | از نوع Business |
| مجوز `instagram_business_basic` | نیازمند App Review |
| مجوز `instagram_business_content_publish` | نیازمند App Review جداگانه |
| **App Review** | ۲ تا ۴ هفته، با ویدئوی نمایش عملکرد و صفحه حریم خصوصی |
| **Business Verification** | تأیید هویت کسب‌وکار با مدارک |

محدودیت‌ها بعد از تأیید: **۲۵ پست در ۲۴ ساعت** برای هر اکانت و ۲۰۰ فراخوانی API در ساعت.

### ⚠️ ریسک واقعی که باید بدانید

برای یک کسب‌وکار ایرانی، **Business Verification متا ممکن است رد شود** — به دلیل تحریم‌ها و اینکه متا مدارک ایرانی را نمی‌پذیرد. این ریسک واقعی است و نباید کل پروژه را به آن گره بزنیم.

**پس معماری را طوری می‌سازیم که اگر اینستاگرام هرگز خودکار نشد، پروژه همچنان کار کند.**

## ۳٫۳ راه‌حل: مدل چهار لایه‌ای انتشار

کانال‌ها را بر اساس «قطعیت خودکارسازی» دسته‌بندی می‌کنیم:

### 🟢 لایه ۱ — کاملاً خودکار، بدون هیچ مانعی (از روز اول)
| کانال | وضعیت |
|---|---|
| تلگرام | ✅ Bot API آزاد، کد شما آماده است |
| بله | ✅ Bot API، بدون محدودیت |
| ایتا | ✅ Bot API، بدون محدودیت |
| روبیکا | ✅ Bot API، بدون محدودیت |
| سایت و بلاگ | ✅ کد خودمان |
| پیامک | ✅ پنل ایرانی |

**این‌ها ۱۰۰٪ خودکارند و هیچ وابستگی به متا ندارند.** برای بازار ایران، همین‌ها موتور اصلی فروش‌اند.

### 🟡 لایه ۲ — خودکار با کمی کار (هفته ۳-۶)
| کانال | پیش‌نیاز |
|---|---|
| پینترست | API ساده، ثبت‌نام آسان، بدون App Review سنگین |
| یوتیوب | Google Cloud + OAuth — نسبتاً آسان |
| آپارات | آپلود با API یا اتوماسیون سبک |
| لینکدین | کد شما از قبل آماده است |
| واتساپ | Green API یا Business API |

### 🟠 لایه ۳ — اینستاگرام نیمه‌خودکار (از روز اول کار می‌کند) ⭐
**این مهم‌ترین ایده این سند است.**

سیستم **همه‌چیز را کاملاً آماده می‌کند** و فقط آخرین کلیک با انسان است:

```
محصول ساخته می‌شود
   ↓
تصویر/کاروسل/ریلز رندر می‌شود
   ↓
کپشن + هشتگ تولید می‌شود
   ↓
همه در «صف انتشار اینستاگرام» می‌رود
   ↓
📱 پیام در تلگرام مدیر:
   [تصویر آماده]
   کپشن آماده (قابل کپی با یک لمس)
   دکمه‌ها: ✅ منتشر شد   ✏️ ویرایش   ❌ رد
   ↓
مدیر تصویر را ذخیره می‌کند، کپشن را کپی می‌کند،
در اینستاگرام پیست می‌کند — ۲۰ ثانیه کار
   ↓
دکمه «منتشر شد» را می‌زند → سیستم ثبت می‌کند
```

**زمان انسانی: ۲۰ تا ۳۰ ثانیه برای هر پست.** با ۲ پست در روز یعنی **یک دقیقه در روز**. این عملاً یعنی اتوماسیون، بدون هیچ وابستگی به متا.

مزیت بزرگ: **از روز اول کار می‌کند**، بدون انتظار ۴ هفته‌ای، بدون ریسک رد شدن.

### 🔵 لایه ۴ — اینستاگرام کاملاً خودکار (اگر App Review پاس شد)
اگر تأیید متا گرفته شد، فقط یک متغیر عوض می‌شود:
```bash
INSTAGRAM_MODE=auto      # به‌جای semi
```
و همان صف، به‌جای فرستادن به تلگرام، مستقیم منتشر می‌کند. **بقیه کد تغییر نمی‌کند.**

## ۳٫۴ مسیر تلاش برای App Review (موازی، بدون توقف پروژه)

اگر خواستید تلاش کنید، ترتیب درست این است:

| گام | کار | زمان |
|---|---|---|
| ۱ | اکانت اینستاگرام را به Professional (Business) تبدیل کنید | ۵ دقیقه |
| ۲ | یک صفحه فیسبوک بسازید و به اینستاگرام وصل کنید | ۱۵ دقیقه |
| ۳ | اپ Business در `developers.facebook.com` بسازید | ۳۰ دقیقه |
| ۴ | صفحه حریم خصوصی و شرایط استفاده روی سایت | ۱ ساعت |
| ۵ | با ۲۵ کاربر تستی، جریان کامل را پیاده کنید | ۲-۳ روز |
| ۶ | ویدئوی نمایش عملکرد ضبط کنید (اجباری) | ۱ ساعت |
| ۷ | درخواست `instagram_business_content_publish` | ۲-۴ هفته انتظار |
| ۸ | Business Verification با مدارک | ⚠️ ریسک رد شدن |

**در تمام این مدت، پروژه با لایه ۳ کار می‌کند و فروش دارد.**

## ۳٫۵ گزینه‌های جایگزین (اگر App Review رد شد)

| گزینه | مزیت | ریسک |
|---|---|---|
| سرویس واسط (Buffer، Later، Publer) | خودشان تأیید متا دارند | هزینه دلاری + پرداخت از ایران سخت |
| اپ موبایل با Share Extension | یک لمس، بدون کپی-پیست | نیاز به توسعه اپ |
| **باقی ماندن روی لایه ۳** | ✅ قابل اتکا، بدون هزینه، بدون ریسک | ۱ دقیقه کار روزانه |

**توصیه صادقانه من:** لایه ۳ را بسازید و آن را کافی بدانید. تلاش برای App Review را موازی انجام دهید ولی **هیچ برنامه‌ای را به آن گره نزنید.**

# مانع ۴ — طراحی و اجرای کل پروژه توسط ایجنت هوش مصنوعی

## ۴٫۱ چه چیزی ایجنت را موفق یا شکست‌خورده می‌کند

ایجنت وقتی خوب کار می‌کند که بتواند **خودش نتیجه کارش را ببیند و تأیید کند**. ایجنتی که کور کار می‌کند، خراب‌کاری می‌کند.

| ایجنت شکست می‌خورد وقتی | ایجنت موفق می‌شود وقتی |
|---|---|
| ❌ کار دستی لازم باشد | ✅ هر کار یک دستور دارد |
| ❌ نتواند خروجی را تست کند | ✅ endpoint سلامت دارد |
| ❌ محیط غیرقابل پیش‌بینی | ✅ محیط قطعی و مستند |
| ❌ خطاها بی‌صدا باشند | ✅ خطا با پیام روشن برمی‌گردد |
| ❌ نداند چه کاری مجاز است | ✅ قوانین صریح در AGENTS.md |

## ۴٫۲ پنج ستون معماری ایجنت‌محور

### ستون ۱ — همه‌چیز یک دستور دارد
هیچ کاری نباید «توی پنل برو و کلیک کن» باشد.

```bash
npm run setup          # آماده‌سازی محیط از صفر
npm run dev            # اجرای محلی
npm run build          # ساخت
npm run deploy         # دیپلوی کامل + تأیید
npm run verify         # تست سلامت همه‌چیز
npm run seed           # داده نمونه
npm run agent:task     # اجرای یک وظیفه از صف
npm run doctor         # تشخیص مشکلات محیط
```

### ستون ۲ — خود-تأییدی (Self-Verification)
هر تغییری که ایجنت می‌دهد، باید بتواند بلافاصله تأیید کند:

```
POST تغییر → npm run verify → آیا سبز شد؟
                   ↓ نه
              rollback خودکار + گزارش خطا
```

Endpointهای تأیید:
| مسیر | چه چیزی را تأیید می‌کند |
|---|---|
| `/api/health` | اپ زنده است، نسخه و کامیت فعلی |
| `/api/health?db=1` | دیتابیس وصل است |
| `/api/health?deep=1` | همه سرویس‌ها: AI، ذخیره‌سازی، صف |
| `/api/admin/integrations-test` | همه توکن‌های شبکه‌های اجتماعی سالم‌اند |
| `/api/admin/ai-test` | AgentRouter پاسخ می‌دهد + تأخیر |

### ستون ۳ — قرارداد ایجنت (AGENTS.md)
یک فایل در ریشه پروژه که به ایجنت می‌گوید چه بکند و چه نکند:

```markdown
## مجاز
- ویرایش app/، lib/، components/، docs/
- ساخت migration جدید در db/migrations/
- اجرای npm run verify بعد از هر تغییر

## ممنوع (بدون تأیید صریح انسان)
- تغییر .env یا هر فایل حاوی کلید
- حذف یا تغییر migration های اجراشده
- دیپلوی روی production
- تغییر قیمت محصولات یا موجودی
- ارسال پیام واقعی به مشتریان
- هر عملیات مالی

## قوانین
- هر PR باید npm run verify را پاس کند
- هیچ کلیدی در کد hardcode نشود
- هر تابع جدید باید تست داشته باشد
- پیام‌های کامیت فارسی یا انگلیسی روشن
```

### ستون ۴ — محیط قطعی (Deterministic)
```
.nvmrc                  → نسخه دقیق Node
package-lock.json       → نسخه دقیق پکیج‌ها
db/migrations/          → شماره‌گذاری‌شده و بازگشت‌پذیر
docs/RUNBOOK.md         → هر عملیات با دستور دقیق
scripts/doctor.sh       → تشخیص انحراف محیط
```

### ستون ۵ — صف وظایف قابل خواندن توسط ماشین
به‌جای اینکه هر بار توضیح بدهید، وظایف در قالب ساختاریافته باشند:

```yaml
# tasks/T-042.yml
id: T-042
title: افزودن توصیه‌گر سایز به صفحه محصول
priority: high
files:
  - app/(shop)/products/[slug]/page.tsx
  - lib/tryon/fit-engine.ts
acceptance:
  - دکمه «پرو کن» در صفحه محصول دیده شود
  - با ورود قد و وزن، سایز پیشنهادی برگردد
  - npm run verify سبز باشد
  - Lighthouse بالای ۹۰ بماند
forbidden:
  - تغییر ساختار جدول products
```

## ۴٫۳ تقسیم کار: ایجنت چه کند، انسان چه کند

| ✅ ایجنت انجام می‌دهد | ❌ فقط انسان |
|---|---|
| نوشتن و ریفکتور کد | خرید دامنه و هاست |
| ساخت migration دیتابیس | ثبت اینماد و مدارک قانونی |
| تولید محتوا و کپشن | تأیید نهایی قیمت محصولات |
| ساخت و اجرای تست | ساخت اکانت شبکه‌های اجتماعی |
| دیپلوی به staging | دیپلوی نهایی production |
| رفع باگ و بهینه‌سازی | مذاکره با تأمین‌کننده |
| نوشتن مستندات | تصمیم استراتژیک |
| تحلیل داده و گزارش | پاسخ به شکایت جدی مشتری |

## ۴٫۴ گاردریل‌های ایمنی (بسیار مهم)

چون این پروژه با پول واقعی و مشتری واقعی سروکار دارد:

| گاردریل | پیاده‌سازی |
|---|---|
| **حالت خشک (Dry-run)** | هر عملیات انتشار یا پیامک، اول در حالت شبیه‌سازی |
| **سقف مصرف** | حداکثر هزینه AI روزانه، حداکثر پیامک روزانه |
| **کلید قرمز** | `AUTOMATION_MODE=PAUSE` همه‌چیز را فوراً متوقف می‌کند |
| **لاگ حسابرسی** | هر تغییر قیمت، موجودی و انتشار ثبت شود |
| **بازگشت خودکار** | اگر health check بعد از دیپلوی قرمز شد، rollback |
| **جداسازی محیط** | staging کاملاً جدا از production با دیتابیس جدا |
| **بدون دسترسی مالی** | ایجنت هرگز به درگاه پرداخت یا حساب بانکی دسترسی ندارد |

## ۴٫۵ چرخه کاری با ایجنت

```
۱) شما: «این کار را بکن»  (یا یک فایل task)
        ↓
۲) ایجنت: می‌خواند، برنامه می‌دهد، تأیید می‌گیرد
        ↓
۳) ایجنت: کد می‌نویسد در یک برنچ جدا
        ↓
۴) ایجنت: npm run verify — خودش تست می‌کند
        ↓
۵) ایجنت: دیپلوی روی staging + health check
        ↓
۶) شما: نگاه می‌کنید، تأیید می‌کنید
        ↓
۷) دیپلوی روی production + تأیید نهایی
        ↓
۸) اگر قرمز شد → rollback خودکار
```
